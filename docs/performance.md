## Reproducible method

`pnpm evidence performance` runs a separate Playwright configuration, one worker, zero retries, fresh browser contexts and local-only requests. It builds production code with the existing explicitly gated test hooks. Desktop viewport is 1280×720 at the Desktop Chrome device defaults and selected High; mobile is Pixel 5 **emulation** with selected Low. Both use Chromium/SwiftShader; no CPU/network throttling claims are made. The report includes actual viewport, drawing buffer, DPR, requested/current quality, reduced-motion state, renderer/vendor, browser version, user agent, host OS, CPU and RAM, timestamp, head and dirty flag.

Each scenario starts from the same seed/spawn and issues one fixed 1/60-second forward-run step per animation-frame callback: 60 warmup frames, then exactly 300 retained samples. The 360 steps cross a substantial part of the sphere along an identical route. Simulation is deterministic; elapsed timing is measured, never claimed to be deterministic. No retries, outlier trimming, frame-interval filtering or automatic quality downgrades select flattering results. Test mode freezes ambient variation and the adaptive RAF loop. The test fails on hidden document, lost context, unexpected quality/pause, model fallback, missing counters, unknown allocation formats, errors or the fixed sampling deadline: **300 seconds for High, 120 seconds for Low**, with a further 30 seconds per test for setup/reporting. These are collection limits, not performance budgets.

### Timeout diagnosis and bounded repair (base `48964a307e03f626433852e205f6d1e8cf01028a`)

The parent's `performance-2026-09-08T08-25-20-086Z.log` records High failing the internal 120-second deadline (121.086 seconds for the test), while Low completed in 21.060 seconds. The wrapper recorded a clean, unchanged exact head, exit 1 and `timedOut: false`. The error context shows selected High and running status. The in-page timer executed, so this is not evidence of a permanently blocked JavaScript task. The old failure path discarded frame progress: a stalled RAF or intermittent renderer stall cannot be excluded. **An unsuitable software-renderer collection limit is the leading diagnosis, not a proven deadlock or a proven High completion time.**

The Low attachment contains 360 completed simulation steps (6 simulated seconds), 300 retained samples and 19.935 seconds of sampling on a two-logical-CPU, approximately 2 GB Linux VM using SwiftShader. Its drawing buffer was 275×508. High is configured for 1280×720 at DPR 1: about 6.6 times those pixels, plus bloom/SMAA, more geometry and 1024 versus 256 shadow-map dimensions. Scaling only Low duration by pixels gives roughly 132 seconds, already beyond the old limit. This is a plausibility check, **not a runtime prediction**: passes, geometry, RAF pacing and software-renderer scheduling do not scale uniformly. Five minutes allows 833 ms per step averaged over the unchanged 360 steps, 2.5 times the old allowance, and about 2.3 times that crude pixel comparison. It is a fixed CI resource allowance selected before the next run, not a fitted confidence bound. Completion on the repaired head remains unverified until the parent runs it after the implementing agent exits.

Low's existing RAF p95 was 66.7 ms (target 33.333 ms: fail); its instrumented completed-frame p95 was 3 ms. Collection passed with cost budgets still pending. This discrepancy reinforces that synchronous service time is not presented frame rate; both series remain in every complete report. No High timing percentiles can be inferred from its timeout. Historical Low evidence does not establish a pass for a subsequent repaired head, desktop hardware or a physical phone.

`scripts/lib/performance-workload.mjs` fixes sample counts and timeout layers without environment overrides. One worker runs at most 330 seconds of High and 150 seconds of Low test time; server build/readiness has 180 seconds. The 720-second Playwright global cap includes 60 seconds of margin over that 660-second sum. The evidence runner applies a separate 780-second process-group deadline, then SIGKILL after 5 seconds if needed. This leaves over six minutes of the existing 20-minute CI job for other gates and artifact handling; the base run's pre-performance gates occupied roughly four minutes locally. That is bounded headroom, not a guarantee against slow dependency installation or other CI contention. A blocked browser cannot extend the job indefinitely, and cancellation/failure is never a pass.

The browser loop checks elapsed time before and after each synchronous step/finish, including the final frame, because a timer alone cannot interrupt synchronous rendering. It checks running/quality after stepping as well. Schema 2 reports include the fixed workload and frame progress. A responsive-page failure attaches `performance-incomplete.json` with reason, completed-frame count, last-progress elapsed time, raw partial samples, state, renderer/host and exact-head metadata, then fails without producing summary percentiles. A hard browser hang may prevent that attachment; outer test/process deadlines still fail the command. Never treat partial samples as a shortened baseline or retry until a favorable completion. Probe completeness, model and console checks and strict pending-budget rejection remain enforced.

`completedFrameMs` spans fixed simulation, all render passes and `gl.finish()` GPU completion. It is synchronous CPU-plus-GPU service time under instrumented test conditions, **not GPU-only timing or presented fps**. `cadenceMs` records raw RAF intervals, including scheduler delay and slow frames. Medians, nearest-rank p95/p99, maxima, sample count and budget exceedances retain stalls. `longIntervals` counts intervals over 1.5× the target; compositor dropped frames cannot be measured by this API. Per-report duration includes warmup; sum the 300 raw cadence intervals for the retained sampling duration. Synchronization and API instrumentation add overhead and exist only in the browser fixture, never product code.

Draw calls and triangles are counted at WebGL draw entry points, including scene, shadows, normal and postprocessing passes and instancing. They are submitted work, not visible polygons. Frame counters reset immediately before each measured simulation/render. This avoids Three.js's per-pass `renderer.info` reset and final-pass-only undercounts.

Texture storage is a **logical allocation estimate** from observed WebGL texture dimensions, levels and format bytes, including render-target textures, depth textures, lookup textures and mipmaps. Counters account for deletion/redefinition and retain a peak since context construction. DEPTH_COMPONENT24 counts a four-byte storage unit conservatively. Driver compression, alignment, hidden copies, framebuffer/renderbuffer storage, multisampling, geometry, JS heap and total device VRAM are excluded. Unknown/compressed/copy allocation paths mark the probe incomplete and fail the test rather than assuming zero. Peak includes startup and quality selection; per-frame summaries use live bytes. Live and startup-peak bytes both compare against the memory ceiling; draw-call, triangle and memory limits use maxima, while timing limits use p95. Review both before assigning memory ceilings. The fixture's finite scene allocations and 360-frame cap bound retained probe data.

Startup is navigation time origin to the browser runner's first observation of visible **Enter Chardin**, including hydration, dynamic runtime import, traveler, SMAA and warmup. It excludes gesture delay and includes observation overhead. It measures the runtime's initial profile (recorded separately), before explicit High/Low selection; it must not be labeled cold High-profile startup. New contexts have empty browser caches, but local server/OS caches are not flushed; there is no simulated network condition. `startupContentMs` remains the much narrower content-construction diagnostic, never total startup.

Resource Timing records encoded/decoded/transfer sizes by local path. The loaded-model summary sums `/models/` encoded bytes; this is not total network transfer. `pnpm evidence bundle`, immediately after `pnpm evidence build`, separately inventories **every** production `.next/static` JS/CSS file, hashes bytes, and sums individual gzip-level-9 sizes. It intentionally counts all client output, including lazy chunks, rather than claiming an initial-route transfer figure. Build ID, clean tree and production build stamp must match; hook-enabled builds cannot masquerade as the ordinary bundle.
